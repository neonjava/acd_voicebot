# W4 Week 1 — approval-safe mock workflow

Related to issue #6. This module implements the provisional team contract in
`docs/contracts.md`. It has exactly two in-memory tools: `echo_text` returns its
text and `mock_save_note` returns a simulated saved-note message. It never
writes a note, calls a shell, opens a browser, or sends a message.

The input is a validated `WorkflowPlan` plus optional `ApprovalRequest` values.
`execute` checks every tool name and exact argument shape, then checks every
approval against the session, plan, and step IDs **before any tool runs**. A
missing or pending required approval returns `awaiting_approval` (or `paused`
for a running plan); rejection returns `cancelled` with zero tool calls. A plan
cannot set `requires_approval=False` to bypass the registry's consequential
policy for `mock_save_note`. Approved steps run in plan order and return a
`WorkflowResult` with outputs keyed by step ID. Invalid plans and mismatched
approvals raise validation errors. A mock tool failure returns a safe error
without exposing the exception text.

The state machine allows only the transitions listed in `docs/contracts.md`.
The executor enforces approval separately from state legality. Each call is a
single in-memory run; durable resume and idempotency across calls are not
implemented in Week 1.

# W4 Week 2 — plan validation, scoped tools, approval expiry and safe executor

Related to issue #33. Week 2 extends the Week 1 executor; the Week 1 call
`execute(plan, approvals=...)` behaves as before and now also returns
`audit_events`.

## What changed

| Area | Behavior |
|---|---|
| Dependencies | `WorkflowStep.depends_on` lists step IDs. `plan_validation.execution_order` rejects unknown dependencies (`WORKFLOW_MISSING_DEPENDENCY`) and cycles (`WORKFLOW_DEPENDENCY_CYCLE`) before any tool runs. Steps run in dependency order; ties keep plan order. Self and duplicate dependencies fail contract validation. |
| Tool registry | `tools.TOOL_POLICIES` is the allow-list: `echo_text` (scope `text:read`, idempotent) and `mock_save_note` (scope `notes:write`, consequential, not idempotent). Arguments must be exactly `{"text"}`, nonblank, at most 1000 characters. Unknown tools → `WORKFLOW_UNKNOWN_TOOL`; bad arguments → `WORKFLOW_INVALID_ARGUMENTS`. |
| Scopes | `execute(..., granted_scopes=frozenset(...))`. A step whose tool scope is not granted → `WORKFLOW_SCOPE_DENIED` before any tool runs. The mock default grants both scopes because both tools are harmless. |
| Approvals | `ApprovalRequest.expires_at` (optional, UTC). Expiry needs an injected `clock`; an approval is expired when `expires_at <= now`. A rejected or expired approval cancels the plan with zero tool calls and records `approval_rejected` / `approval_expired`. Expiry is checked again before every step and retry: an approval that runs out mid-run stops the remaining work, keeps earlier outputs and records `approval_expired`. Approvals still must match session, plan and step IDs. |
| Audit | `WorkflowResult.audit_events` lists `AuditEvent` records in order (`sequence`). They hold IDs, kind and redacted details only — never tool arguments, outputs or exception text. |
| Timeouts | `step_timeout_ms` with an injected `clock`. The tool runs on a daemon thread and the executor stops waiting at the deadline, so a blocked tool cannot hold the caller. A timed-out step has its output discarded (`WORKFLOW_STEP_TIMEOUT`). A tool may also raise `TimeoutError`, and the injected clock can simulate an overrun in tests. Without `step_timeout_ms` or a `CancellationToken`, tools run on the calling thread as in Week 1. |
| Retries | `max_retries` (default 0). Only idempotent tools are retried, and only for timeouts or `TransientToolError`. `mock_save_note` is never called twice in one run. Other exceptions fail at once with `WORKFLOW_TOOL_FAILED`. |
| Cancellation | `CancellationToken.cancel()` is checked before the run, before every step and before every retry, and it also stops the executor waiting for a tool that is running. Cancelled runs return `cancelled` with outputs of completed steps. |

Policy errors raise `WorkflowPolicyError` (a `ValueError`) with `.code`;
`to_envelope(correlation_id)` gives a safe `ErrorEnvelope` for W5.

## Week 1 vs Week 2 guarantees

Week 1: one in-memory call, no retries. Week 2: within **one call**, retries are
bounded and limited to idempotent tools, so a consequential step cannot be
replayed by the retry loop. There is still no durable history: calling
`execute` again with the same approved plan runs it again. Durable
idempotency across calls is not implemented.

A timeout or cancel stops the executor waiting; it does not stop the tool. Python
cannot kill a thread, so a blocked tool keeps running in the background and its late
result is ignored. Treat the effect of an abandoned call as unknown: this is why
only idempotent tools are retried. A future tool with real side effects needs
its own cancellation or a process boundary, not only this deadline.

## Week 3 (#68): checkpoint and resume, audit progress, approvals, first real tools

Product context: [product.md](product.md). This is Jarvis's "hands": safe
tools run directly, consequential tools always wait for approval.

### What was added

| Piece | File | What it does |
|---|---|---|
| Checkpoints and resume | `agent/checkpoint.py`, `executor.py` | `WorkflowStore` remembers each succeeded step and its output. Running the same plan again after a failure skips those steps (audited as `step_restored`) and never calls their tools again, including consequential ones. A succeeded plan's checkpoint is cleared. A step that needs approval and timed out (even if the tool returned after the deadline) or was cancelled while its tool ran has an unknown outcome: the checkpoint records it with the approval ID used, and a resume with that same approval runs nothing and ends `awaiting_approval` (`paused` from `running`), audited as `approval_missing` with `reason=previous_outcome_unknown`. Safe steps that timed out simply rerun. **Spent approvals:** an approval-gated step spends its approval when it succeeds or when its outcome is unknown; the store remembers every spent approval ID per plan and step (also after a succeeded plan's checkpoint is cleared) and the executor ignores them, so one approval runs its step at most once. Running the step again needs a fresh approval with a new `approval_id` (`approval_missing` with `reason=previous_outcome_unknown` or `approval_already_used` until then). A step whose tool failed outright does not spend its approval, so a resume retries it. Only one run of a plan at a time per store: an overlapping run gets `WORKFLOW_RUN_IN_PROGRESS` before any tool runs. All store methods are thread-safe; the store keeps the newest 1000 plans per kind of record. |
| Idempotency keys | `executor.py` | `execute(..., store=..., idempotency_key=...)`: only a `succeeded` or `cancelled` result is stored; the same key for the same plan returns it without running anything. A `failed` run and an unfinished one (awaiting approval) are not stored, so retrying with the same key resumes from the checkpoint and approving and re-running works. The same key for a different plan is `WORKFLOW_IDEMPOTENCY_CONFLICT`. The key is reserved while its run is in progress: an overlapping call with the same key gets `WORKFLOW_IDEMPOTENCY_IN_PROGRESS` before any tool runs. |
| Progress events | `executor.py`, `agent/progress.py` | `on_audit` receives every `AuditEvent` as it happens (a broken listener never stops the run). `audit_envelopes(...)` wraps them as `workflow.audit` events (producer `workflow`) for the W5 session stream. Audit records never contain tool arguments or outputs. |
| Proposals from reasoning | `agent/proposals.py` | `plan_from_proposal(proposal)` validates every step (known tool, exact arguments, allow-listed site, no missing dependency or cycle) and returns a draft `WorkflowPlan`. A proposal step marked `requires_approval=False` cannot skip approval for a consequential tool. |
| Approvals from the backend | `agent/approvals.py` | `execute(..., approval_source=...)` reads decisions from anything with `approvals_for_plan(plan_id)`. `approval_requests_for(plan, now=...)` creates expiring requests for the steps that need approval. `InMemoryApprovalSource` is the mock backend: deciding twice is `APPROVAL_ALREADY_DECIDED`, deciding after expiry is `APPROVAL_EXPIRED`. **Re-approval:** `reapproval_requests_for(plan, store, now=...)` returns new pending requests (`{plan_id}-approval-{step_id}-N`, the lowest unused `N >= 2`) for steps whose approval is spent; the backend registers them and the UI decides them like any other request. With a store, the executor sets spent approvals aside before matching, so the old and the fresh request for one step are not duplicates. W5's session service provides the real source after integration. |
| `system_stats` tool | `agent/tools.py`, `agent/system_tools.py` | Safe, read-only, no arguments. RAM and CPU usage plus the top 5 programs by memory, grouped by program (all Chrome processes count as "chrome"). Real mode uses psutil (`system` extra, imported lazily) and the executable's file name, because Linux truncates process names. |
| `open_url` tool | `agent/tools.py` | Safe only for `https` links on allow-listed sites (default `youtube.com`, `github.com` and their subdomains). `file:`, `javascript:`, `http:`, other hosts, look-alike hosts, links with credentials, links Python cannot parse (for example `https://[x` or characters that change under NFKC), links containing a backslash (browsers read it as `/`, so `https://evil.example\.youtube.com` would open `evil.example`) and hosts that are not plain ASCII DNS names are rejected before any step runs. Not idempotent, so it is never retried. |
| Tool runtime | `agent/tools.py` | `ToolRuntime` decides where data and side effects come from. Mock is the default (fixture stats, URLs only recorded). `runtime_from_env()` reads `WORKFLOW_TOOLS_MODE=mock|real` and `WORKFLOW_ALLOWED_HOSTS=youtube.com,github.com`. |

No shell commands, file deletion, or keyboard and mouse control exist.

### Inputs, outputs and one failure path

- **Input:** a `WorkflowProposal` from W3, approval decisions from the backend,
  and optionally a `WorkflowStore`, an idempotency key and an audit listener.
- **Output:** a `WorkflowResult` (state, outputs, safe error, audit events) and
  live `workflow.audit` progress.
- **Failure path:** a step fails, so the run ends `failed` with a safe
  `WORKFLOW_TOOL_FAILED` error. Running the plan again with the same store
  (and the same idempotency key, if one was used) restores the completed steps
  and continues from the failed one.
