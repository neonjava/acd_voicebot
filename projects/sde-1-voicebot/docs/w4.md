# W4 Week 1 — approval-safe mock workflow

Related to issue #6. This module implements the provisional team contract in
`docs/contracts.md`. It has exactly two in-memory tools: `echo_text` returns its
text and `mock_save_note` returns a simulated saved-note message. It never
writes a note, calls a shell, opens a browser, or sends a message.

The input is a validated `WorkflowPlan` plus optional `ApprovalRequest` values.
`execute` checks every tool name and exact argument shape, then checks every
approval against the session, plan, and step IDs **before any tool runs**. A
missing or pending required approval returns `awaiting_approval` (or `paused`
for a running plan); rejection returns `cancelled` with zero tool calls. A plan
cannot set `requires_approval=False` to bypass the registry's consequential
policy for `mock_save_note`. Approved steps run in plan order and return a
`WorkflowResult` with outputs keyed by step ID. Invalid plans and mismatched
approvals raise validation errors. A mock tool failure returns a safe error
without exposing the exception text.

The state machine allows only the transitions listed in `docs/contracts.md`.
The executor enforces approval separately from state legality. Each call is a
single in-memory run; durable resume and idempotency across calls are not
implemented in Week 1.

# W4 Week 2 — plan validation, scoped tools, approval expiry and safe executor

Related to issue #33. Week 2 extends the Week 1 executor; the Week 1 call
`execute(plan, approvals=...)` behaves as before and now also returns
`audit_events`.

## What changed

| Area | Behavior |
|---|---|
| Dependencies | `WorkflowStep.depends_on` lists step IDs. `plan_validation.execution_order` rejects unknown dependencies (`WORKFLOW_MISSING_DEPENDENCY`) and cycles (`WORKFLOW_DEPENDENCY_CYCLE`) before any tool runs. Steps run in dependency order; ties keep plan order. Self and duplicate dependencies fail contract validation. |
| Tool registry | `tools.TOOL_POLICIES` is the allow-list: `echo_text` (scope `text:read`, idempotent) and `mock_save_note` (scope `notes:write`, consequential, not idempotent). Arguments must be exactly `{"text"}`, nonblank, at most 1000 characters. Unknown tools → `WORKFLOW_UNKNOWN_TOOL`; bad arguments → `WORKFLOW_INVALID_ARGUMENTS`. |
| Scopes | `execute(..., granted_scopes=frozenset(...))`. A step whose tool scope is not granted → `WORKFLOW_SCOPE_DENIED` before any tool runs. The mock default grants both scopes because both tools are harmless. |
| Approvals | `ApprovalRequest.expires_at` (optional, UTC). Expiry needs an injected `clock`; an approval is expired when `expires_at <= now`. A rejected or expired approval cancels the plan with zero tool calls and records `approval_rejected` / `approval_expired`. Expiry is checked again before every step and retry: an approval that runs out mid-run stops the remaining work, keeps earlier outputs and records `approval_expired`. Approvals still must match session, plan and step IDs. |
| Audit | `WorkflowResult.audit_events` lists `AuditEvent` records in order (`sequence`). They hold IDs, kind and redacted details only — never tool arguments, outputs or exception text. |
| Timeouts | `step_timeout_ms` with an injected `clock`. The tool runs on a daemon thread and the executor stops waiting at the deadline, so a blocked tool cannot hold the caller. A timed-out step has its output discarded (`WORKFLOW_STEP_TIMEOUT`). A tool may also raise `TimeoutError`, and the injected clock can simulate an overrun in tests. Without `step_timeout_ms` or a `CancellationToken`, tools run on the calling thread as in Week 1. |
| Retries | `max_retries` (default 0). Only idempotent tools are retried, and only for timeouts or `TransientToolError`. `mock_save_note` is never called twice in one run. Other exceptions fail at once with `WORKFLOW_TOOL_FAILED`. |
| Cancellation | `CancellationToken.cancel()` is checked before the run, before every step and before every retry, and it also stops the executor waiting for a tool that is running. Cancelled runs return `cancelled` with outputs of completed steps. |

Policy errors raise `WorkflowPolicyError` (a `ValueError`) with `.code`;
`to_envelope(correlation_id)` gives a safe `ErrorEnvelope` for W5.

## Week 1 vs Week 2 guarantees

Week 1: one in-memory call, no retries. Week 2: within **one call**, retries are
bounded and limited to idempotent tools, so a consequential step cannot be
replayed by the retry loop. There is still no durable history: calling
`execute` again with the same approved plan runs it again. Durable
idempotency across calls is not implemented.

A timeout or cancel stops the executor waiting; it does not stop the tool. Python
cannot kill a thread, so a blocked tool keeps running in the background and its late
result is ignored. Treat the effect of an abandoned call as unknown: this is why
only idempotent tools are retried. A future tool with real side effects needs
its own cancellation or a process boundary, not only this deadline.
